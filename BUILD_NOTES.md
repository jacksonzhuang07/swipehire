## v8 — Blob uploads fixed: private-store contract (2026-11-12)
- **The bug (proven on production):** `POST /api/profile/photo` returned 500 — `urllib.error.HTTPError: HTTP Error 400` from `blob_put`. Root cause: the connected store `swipehire-uploads` is a **PRIVATE** store (dashboard: "Private — blobs uploaded here require a token to read"), but v7's PUT was written against the public-store contract and never declared access. Per the Vercel Blob docs, the declared access must match the store, and the raw HTTP API declares it with the header `x-vercel-blob-access: private` on the PUT (alongside `Authorization: Bearer <rw-token>`, `x-api-version: 7`, `x-content-type`). v8 sends exactly that (`storage.BLOB_ACCESS`).
- **Error surfacing:** `_http` now reads the response body on HTTPError and raises `storage.BlobAPIError(status, detail)` with the API's own JSON error message, also logged (`blob API PUT blob.vercel-storage.com failed: HTTP 400: …`). Discarding that body is what made the v7 400 undebuggable. Request headers — the token — are never logged (test asserts this).
- **Serving private blobs:** the v7 `/uploads` 302-redirect cannot work on a private store (the URL needs the token). The route now fetches the object server-side — documented private download: GET on the blob URL with `Authorization: Bearer <token>` (`storage.blob_get`) — and streams the bytes, with the stored content type, to the already session-authorized user (`@login_required` unchanged: anonymous requests still get 401). A failed fetch returns 502, never a redirect. Net effect: **access control is enforced on the blob backend too** — the v7 "public-if-known" note below is superseded; the blob URL never reaches the browser and is useless without the token anyway.
- **Delete:** unchanged wire shape (POST `/delete`, URL list, same Bearer auth) — that contract is identical on a private store; it now surfaces failures as `BlobAPIError` (still never raised to callers — `delete_upload` stays best-effort). Document text remains the DB source of truth; blob document mirrors follow the same PUT/GET/DELETE rules.
- **Tests: 103 passed in one clean final pass** (99 v7 + 4 net-new/changed in `tests/test_storage.py`: PUT asserts the `x-vercel-blob-access: private` header, blob GET wire shape, `/uploads` proxies bytes instead of redirecting + 401 for anonymous + 502 on fetch failure, HTTPError body propagation into exception and log with the token absent). Health reports version 8; web assets `?v=8`.
- **Verification honesty:** blob-path tests mock the `_http` choke point (no token in this VM) — the wire contract is implemented from the documented API and the established production diagnosis, but the final proof is the live re-test on production after this deploy (photo upload → 200, photo view → bytes), which the parent runs.

## v7 — Vercel Blob storage for uploads (2026-11-12)
- **Storage layer** `app/storage.py`, two backends selected purely by env: `BLOB_READ_WRITE_TOKEN` set → **blob** (Vercel Blob over its HTTP API, stdlib `urllib` only — no new dependency; single `_http` choke point), absent → **local** filesystem exactly as before (dev/tests unchanged; the full suite passes with no token anywhere near the test env, and the token is never needed in this VM).
- **Per-backend behaviour:**
  - *Photos / employer logos* — saved via `storage.save_upload()` under the same unguessable names as before (`{table}_{row_id}_{uuid10}{ext}`). Blob backend: bytes go to Blob, nothing is written locally, and the put response's public URL is stored on the row (`candidates.photo_blob_url` / `employers.logo_blob_url`, new columns + migrations). Local backend: file written under the uploads dir, blob URL stays `''`.
  - *Documents* — text remains in the DB (source of truth, unchanged). On the blob backend each document's text is additionally mirrored to Blob as `documents_{candidate_id}_{doc_id}_{uuid10}.txt` and the URL stored on `documents.blob_url`; the mirror is best-effort (a failed mirror logs and never breaks the upload).
  - *Serving* — every photo/logo URL in templates and API payloads is produced by `storage.display_url()` and is always the app's own `/uploads/<name>` route: local records serve bytes from disk (session-gated, as before); records with a blob URL get a **302 redirect** to the blob URL. Display code does not branch on backend.
  - *Health* — `/api/health` reports `{"version": 7, "storage": "blob"|"local"}`.
- **Deletion** — document delete and delete-my-account collect the records' blob URLs (photo, logo, every document) and call the Blob delete API (`POST /delete` with the URL list); photo *replacement* also deletes the previous object. All remote deletes go through `storage.delete_upload()`, which **never raises**: a failed remote delete is logged ("object may be orphaned") and the DB flow completes. Local files are unlinked best-effort as before.
- **Access control — the honest note (SUPERSEDED by v8, kept for the record):** v7 assumed the store was public and treated objects as public-if-known. Production proved the store is in fact **private**, and v8 implements the private-store contract (declared access on PUT, server-side proxied GET) — access control IS enforced; see the v8 section.
- **Wire-format caveat:** the Blob HTTP calls follow the documented Blob client API (PUT `https://blob.vercel-storage.com/?pathname=…`, `Authorization: Bearer <token>`, `x-api-version: 7`, `x-content-type`, put returns JSON with the public `url`). This environment has no token, so the blob path is verified by unit tests with the HTTP layer mocked (wire shape, URL stored on the record, redirect, delete + failure tolerance) — it has **not** been live-verified against the real store; first production deploy with the token set is where that check happens.
- **Tests: 99 passed in one clean final pass** (87 v6 + 12 new in `tests/test_storage.py`). Visual QA: `visual-qa/qa.py` gained `storage_shots` — Documents + Profile at 1920×1080 and 390×844 after a real photo upload through the API (200, stored, rendered as the profile avatar at both widths; no horizontal overflow). Server on :5050 restarted, health reports version 7 / storage local. Assets bumped to `?v=7`.

## v6 — AUTONOMOUS extension executor (2026-11-12)

**The extension now applies by itself.** Jackson's requirement: fill AND submit, no human clicks after pairing. Extension v2.0.0 (manifest version bumped; zip at `app/static/swipehire-extension.zip` rebuilt; web assets `?v=6`; health reports version 6).

**Queue processor** (`extension/background.js`, MV3 service worker, `alarms` every 0.5 min + a kick on pairing/toggle): claims one application at a time from `GET /api/ext/queue`, reports `opened`, opens the job URL in a tab it manages (an `about:blank` tab is created FIRST and its id recorded before navigating — a load race otherwise loses the tab binding), and the content script drives the page, reporting through runtime messages → `POST /api/ext/report` events `opened | filling | submitted | needs_human | failed`. A 150s claim watchdog parks a silently-dead claim as `needs_human`. An in-memory tick lock prevents double-claims (async storage reads let two near-simultaneous ticks both pass the busy check — observed live during E2E debugging, then fixed).

**Pacing (hard-coded launch defaults, all counters in `chrome.storage.local` with day rollover, shown in the popup):** ≥90s between submissions; rolling burst cap 5 submissions / 30 min; daily caps per board — LinkedIn 30, Indeed 20, ATS 40. An account-warning signal (checkpoint / "unusual activity" / restricted-account text) parks the job AND auto-pauses the whole processor.

**Safety stops → `needs_human`, never defeated** (detected before any filling, re-checked before every submit click): CAPTCHA/reCAPTCHA (element, iframe, or `data-sitekey`), login wall (password field / sign-in wall / session-expired text), security checkpoint, MFA/verification-code prompts. **Facts-only rule enforced in the driver:** fields are filled ONLY from the application payload's `answers`; a required field/question with no matching stored fact parks the job with the question text in the note (server appends it to `needs_review` + proof). Workday (`ats_account`) parks with "Workday account portals are not automated yet — log in there once…" unless the user is already logged in and the page is a plain form, in which case the generic driver may attempt it.

**Drivers** (`extension/content.js`, fully rewritten; all matching is label/aria/placeholder/text-based, never brittle single class names; every action goes to a run log, last 50 events, viewable in the popup): (a) **Generic ATS / multi-step form driver** — fills text inputs/selects/radios by label matching (name, first/last name, email, phone, LinkedIn, website, location, current title, years of experience, salary expectation, skills), attaches the tailored resume by constructing a `File` from the payload's resume text and assigning it via `DataTransfer`, checks consent/certification checkboxes (never "no"-by-default answers), walks Next/Continue steps, clicks submit, and confirms via thank-you text / confirmation banner / URL change — the evidence sentence is reported as proof. (b) **LinkedIn Easy Apply driver** — clicks Easy Apply, walks the modal (Next → Review → Submit application, ≤8 steps), selects a resume radio when identifiable, parks on unknown required questions; also falls back to the generic walker if the modal shape differs. (c) **Indeed driver** — generic walker + Indeed Apply button detection (best-effort; Indeed's smart-apply iframe flows are a known limitation, below). Drivers key off page structure first, domain second, so company-site forms on unknown domains still get the generic driver.

**Popup** (rewritten): pairing (Save turns Autonomous ON and kicks the processor), a big Pause/Resume, per-board "today x/cap" counters, submissions in the last 30 min, next-allowed time, the run log, and the queue list (clicking a job opens it now — the driver still runs).

**Server/API:** `/api/ext/queue` items now carry `tailored_resume` + structured `answers` enriched live from stored facts (first/last name split, `salary_expectation` from the candidate's stored minimum salary, `years_of_experience` from the Master Profile — new keys also added to `apply_engine.KNOWN_QUESTIONS`). Tracker pill **"Needs you"** (`.st-needs_human`). **Bug the new tests caught and fixed:** v5's queue filter matched `method='extension_required'` regardless of status, so parked/submitted jobs would be re-claimed forever; eligibility is now status-based (`queued_extension`, or `prepared` + extension-required/ATS). ## Honest limitations
- Vercel SQLite is in `/tmp` and **ephemeral** — data resets on cold starts unless the Turso env vars are set. **Uploads (v7/v8):** persistent when `BLOB_READ_WRITE_TOKEN` is set (Vercel Blob); on the local backend they are ephemeral on Vercel too. The store is **private**: `/uploads` is session-gated on both backends and blob bytes are proxied server-side with the token — see the v8 section.
- Apply executor (current, v5/v6): nothing is recorded `submitted` unless the browser extension's driver actually submitted it and detected the site's confirmation (proof carries the confirmation text). Everything else stays honestly labelled — `prepared` (package ready, not sent), `queued_extension`, or `needs_human` (parked with the reason). The autonomous driver is fixture-proven (see v6 section); real-board selector variance, Indeed smart-apply iframes, and Workday account portals park as `needs_human` rather than guessing.
- Tailoring never invents: skills/experience/education come only from Master Profile facts; uncovered job keywords are stored as gaps on the application.
- Screening answers are built only from stored resume facts; unknown questions (work authorization, salary expectation, relocation) are logged as `needs_review`, never invented.
- Employer candidate deck is the marketplace directory (all candidates), as in v1; a user's *own* data (documents, swipes, applications, matches, messages) is strictly scoped to their account.
- Seeded demo accounts all use password `demo` (documented in README) — remove/rotate before any real deployment. Session secret defaults to a dev value unless `SWIPEHIRE_SECRET` is set.
- Salary parsing from Remotive is best-effort regex on its free-text salary field.
