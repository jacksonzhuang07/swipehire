## v5 — LAUNCH pass + browser extension (assisted apply) (2026-11-12)

**Status model (honesty fix).** The apply engine no longer records anything as submitted. External-URL jobs → `prepared` / `external_link`; no-URL jobs → `prepared` / `package_only` (was `simulated_executor`); proof text reads “Application package prepared (tailored resume + answers). Not yet submitted — no executor has sent this.” `submitted` is reachable **only** via `POST /api/ext/report` with event `submitted`. Tracker renders pills: Prepared / Needs extension / Queued for extension / Needs review / Submitted.

**Job classification** (`app/classify.py`, stamped at ingestion in `insert_jobs`, backfilled in `init_db` for existing rows): linkedin.com, indeed.* → `network_login`, 🔒; myworkdayjobs/workday → `ats_account`, 🔒; greenhouse.io, lever.co, ashbyhq.com, workable.com, smartrecruiters.com, breezy.hr, recruitee.com → `ats_form`; everything else / no URL → `external`. 🔒 cards carry a “Login required” badge. 16 parametrized classifier tests.

**Extension model (Jackson's final design).** Extension is an add-on for 🔒 jobs ONLY. Right-swipe on a 🔒 job: extension not connected → `prepared` / `extension_required` + swipe API returns `needs_extension: true` → Tinder-styled modal “This one needs your login” ([Install the SwipeHire extension] → `/extension/download`, [Set it up on Connections], [Later — keep it prepared]); extension connected (pairing token issued AND used, not revoked) → `queued_extension` / `extension`, no prompt.

**Extension v1** (`extension/`, Chrome MV3, no build step; also served as a committed zip at `app/static/swipehire-extension.zip` via `GET /extension/download`): manifest (storage+tabs; host permissions for the app domain + LinkedIn/Indeed/Greenhouse/Lever/Workday), popup (API base + pairing token, queue list, click-to-open + report `opened`), content script (autofills name/email/phone from the queued application's answers in chrome.storage, floating panel with [I submitted it ✓] / [Couldn't apply], confirmation-page detection → report `submitted`). Pairing: `POST /api/ext/pairing-token` returns the plaintext once, stores only a werkzeug hash, regenerating revokes previous tokens; `DELETE` revokes. Token-auth (Bearer, never session) `GET /api/ext/queue` + `POST /api/ext/report` {opened|filled|submitted|failed}; failed → `needs_review`. Validated node-less: manifest JSON parses, `node --check` clean on both JS files. **Honest scope: assisted apply — the human makes the final submit click on the site.** The queue/claim/report shape is deliberately what a future autonomous queue processor needs; Jackson has confirmed autonomous auto-drive as the next step — it is NOT built in v5 (see extension/README.md).

**Connections page** (candidate nav 🔌): Tier 0 active explainer; Tier 1 extension — state pill (Not connected / token issued / connected + last-used), Download zip, Generate/Revoke pairing token (token shown once in a dashed box with Copy); Tier 2 LinkedIn/Indeed identifier-only forms (NO password field anywhere — a test asserts a posted password value never lands in the record), list + Disconnect, status `pending_session`, new `connections` table, per-user isolation + employer 403 tested.

**Persistent DB — Turso/libSQL.** `app/db.py` connection layer: when `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN` are set, `get_conn()` returns `TursoConn` (the local file path argument is intentionally ignored); otherwise local SQLite exactly as before. The wrapper exists because `libsql` (0.1.11, added to both requirements files) returns plain tuples — `_Row` restores name+index access and `dict(row)`, `_Cursor` restores fetchone/fetchall/lastrowid eagerly; `PRAGMA table_info` and `executescript` pass through (verified: libsql supports both); one adaptation was needed — libsql `fetchall()` returns `None` for non-SELECTs, guarded. init_db (schema + migrations + classification backfill) runs unchanged against both backends. **CAVEAT: no live Turso credentials exist in this environment, so the hosted path is code-complete and OFFLINE-tested against a real local libsql database file through the exact wrapper (CRUD, lastrowid, pragma, full init_db, seed_all) — live verification against a real Turso instance happens at deploy time by the parent when the env vars are set.** Uploads still go through `get_uploads_dir()` and remain filesystem/ephemeral on Vercel (documented follow-up: object storage).

**Launch pages + hardening.** `/privacy` + `/terms` in the app design language (data stored, never-store-passwords, demo-mode email disclosure, no data sale, delete = delete). **Delete my account** (Profile → Danger zone, double confirm): deletes user + candidates/employers rows, documents, swipes, applications, matches + their messages, employer jobs and everything referencing them, connections, ext_tokens, login_codes — tested, including re-registering the same email afterwards; the delete test initially caught ext_tokens being missed — fixed. ## v4 — passwordless email-code sign-in + bigger live pool (2026-11-12)

**A. Email-code sign-in** (added *alongside* password login + demo logins; nothing removed)
- Third auth tab “✉️ Email code”: enter email → `POST /api/auth/code/request` → 6-digit code → `POST /api/auth/code/verify` (email + code + optional role/name/company, used only when the email has no account yet; default role candidate) → account created on first verify, session logged in via the existing Flask session.
- Codes: only a werkzeug **hash** is stored (`login_codes` table), **10-minute expiry, single-use, max 5 attempts**, rate limit **3 requests per email per 15 min** (429 after). Request responses are generic — identical shape whether or not the account exists, so existence isn't leaked. Verify failures are one generic 401.
- Delivery is pluggable (`app/mailer.py`): `RESEND_API_KEY` → Resend API (From `SWIPEHIRE_MAIL_FROM` or onboarding@resend.dev); else `SMTP_HOST/PORT/USER/PASS` → smtplib; else **DEMO MODE — no email is sent**: the code is returned in the API response and shown on the auth screen in a clearly-labelled dashed-yellow demo box (“Demo mode: no email service is connected yet, so no email was sent. Your code is …”) and logged server-side. Code-created accounts get an unusable random password hash (code-login only until a password flow exists). Test hook: `SWIPEHIRE_MAIL_CAPTURE=1` captures mail into `mailer.LAST_SENT`.
- Google sign-in was **not** built (needs a Google Cloud OAuth project + client-secret provisioning by Jackson).

## Honest limitations
- Vercel SQLite is in `/tmp` and **ephemeral** — data resets on cold starts; **uploads (photos/logos) are ephemeral there too**. Demo-grade only; swap `app/db.py` to a hosted DB and uploads to object storage for durable production.
- Apply executor: jobs with a real external apply URL are recorded `submitted / external_link`; all other jobs use a **simulated executor, labelled as such in the UI and in the application proof text** — no external submission actually occurs for those.
- Tailoring never invents: skills/experience/education come only from Master Profile facts; uncovered job keywords are stored as gaps on the application.
- Screening answers are built only from stored resume facts; unknown questions (work authorization, salary expectation, relocation) are logged as `needs_review`, never invented.
- Employer candidate deck is the marketplace directory (all candidates), as in v1; a user's *own* data (documents, swipes, applications, matches, messages) is strictly scoped to their account.
- Seeded demo accounts all use password `demo` (documented in README) — remove/rotate before any real deployment. Session secret defaults to a dev value unless `SWIPEHIRE_SECRET` is set.
- Salary parsing from Remotive is best-effort regex on its free-text salary field.
